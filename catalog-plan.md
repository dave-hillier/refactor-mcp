# Plan: Refactoring catalog and fixture-based tests

A stream of work independent of the daemon and CLI work in `plan.md`. The
aim is a catalog of C# refactorings described as behaviour, each backed by
plain input and expected-output files, so the catalog is the specification and
the current implementation is measured against it rather than defining it.

## Why

- Current tests embed input and expected code as string literals inside xUnit
  methods. They are hard to read, hard to diff, and tied to the tool method
  signatures of today.
- There is no single place that says what refactorings exist, what each one
  promises, and what its edge cases are. The README lists tools, not
  refactorings.
- A fixture corpus lets any implementation, current or rewritten, be scored
  against the same expectations. It also serves as documentation and as
  examples for agents using the tool.

## Fixture format

One directory per case, under `Catalog/<refactoring>/<case>/`.

```
Catalog/
  extract-method/
    README.md                     description of the refactoring
    simple-statements/
      case.json                   the operation and its arguments
      before/
        Sample.cs
      after/
        Sample.cs
    multiple-files/
      case.json
      before/
        Order.cs
        Customer.cs
      after/
        Order.cs
        Customer.cs
    expression-bodied-rejected/
      case.json                   expects an error, no after/ directory
      before/
        Sample.cs
```

`case.json` describes the refactoring in terms of the catalog, not the tool
method:

```json
{
  "refactoring": "extract-method",
  "description": "Extracts two statements into a private method",
  "target": { "file": "Sample.cs", "range": "5:9-6:30" },
  "arguments": { "name": "ValidateInputs" },
  "expect": "success"
}
```

For failure cases:

```json
{
  "refactoring": "extract-method",
  "target": { "file": "Sample.cs", "range": "3:35-3:50" },
  "arguments": { "name": "Doubled" },
  "expect": "error",
  "errorContains": "expression-bodied"
}
```

Rules:

- `before/` is a complete, compilable set of files. A single `.csproj` is
  generated by the runner so cases never carry project files.
- `after/` contains every file that should exist afterwards. A file present in
  `before/` and absent from `after/` must have been deleted. A file present
  only in `after/` must have been created.
- Comparison is whitespace-normalised on line endings only. Indentation and
  blank lines are part of the expectation.
- Targets use `line:column` ranges or a symbol name. Symbol targeting
  (`"target": { "file": "Sample.cs", "symbol": "Order.Total" }`) is preferred
  where it removes brittleness.

## Runner

- A single xUnit theory discovers every `case.json` and runs it. Test names
  are `<refactoring>/<case>` so failures point at a directory.
- The runner copies `before/` into a temp project, applies the refactoring
  through a small adapter that maps catalog names and arguments onto the
  current tool methods, then diffs against `after/`.
- Cases for refactorings the implementation does not yet support are marked
  `"status": "unimplemented"` in `case.json` and reported as skipped, not
  failed. The skipped count is the backlog.
- A `--update` mode rewrites `after/` from actual output for reviewing new
  behaviour, never run in CI.
- The runner is the only place the tool method signatures appear. Renaming or
  reshaping a tool changes one adapter entry.

## Catalog

Grouped by what they act on. Each entry gets a `README.md` stating the
precondition, the transformation, what must be preserved, and the known
limitations. The list below is the intended scope regardless of what is

## Case coverage guidance

For each refactoring, aim for at least:

- One minimal happy path.
- One case exercising trivia: comments, regions, pragma directives and blank
  lines adjacent to the edit.
- One case with references in another file, to prove solution-wide edits.
- One case for each documented precondition failure.
- One case with generics, one with overloads, one with inheritance, where the
  refactoring interacts with them.
- One case with `#nullable enable` and nullable annotations.

## Work items

1. Define the `case.json` schema and write the runner with a hand-written
   adapter for one existing refactoring. Prove the discovery, copy, run and
   diff loop on Extract Method.
2. Port the existing string-literal tests for implemented tools into fixture
   directories. Delete the literal-based tests once the fixture version
   passes.
3. Write `README.md` for every catalog entry, including unimplemented ones.
4. Author fixture cases for unimplemented refactorings and mark them
   `unimplemented`. Each becomes a ready-made acceptance test.
5. Add a summary test or script that prints implemented, unimplemented and
   failing counts per category. Use it to prioritise the backlog.
6. Generate `EXAMPLES.md` from the catalog so documentation and tests cannot
   drift.

## Relationship to the daemon work

None at the code level. The runner calls tool methods in-process. When the
CLI stabilises, add a second runner mode that drives cases through the CLI
against a daemon, which doubles as the CLI integration test suite.
